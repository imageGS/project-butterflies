# СБОРКА ЧЕРЕЗ СЦЕНЫ GODOT — ЖЁСТКОЕ ТРЕБОВАНИЕ

> Это не пожелание, а условие приёмки. Если проект нельзя открыть в редакторе, подвигать объекты мышкой и продолжить развитие — задача не выполнена.

---

## 1. Почему это требование

**В прототипе всё строилось из данных в рантайме.** Станция — это ASCII-карта (`.txt`) плюс `StationData` (`.tres`). Геометрия, стены, объекты и сущности создавались кодом при загрузке: `MapManager` строил карту, `EntityManager` спавнил сущности-словари в массив. В редакторе Godot **не было видно ничего** — ни комнаты, ни двери, ни NPC. Только пустая сцена и скрипт.

**Последствия:** нельзя подвинуть стену, не пересчитав ASCII. Нельзя проверить композицию до запуска. Нельзя поправить уровень, не понимая устройство четырёх файлов одновременно. Это главная причина, по которой проект стал тяжело развиваемым.

**Так делать нельзя.** В 3D всё должно быть видно, двигаться и настраиваться руками в редакторе.

---

## 2. Правило

> **Каждый уровень — это сцена. Каждый объект — инстанс сцены. Всё видно в редакторе и двигается мышкой.**

Открыл `station_akio.tscn` — увидел станцию. Потянул дверь — дверь сдвинулась. Поменял текстуру стены в инспекторе — стена поменялась. Запустил — играется ровно то, что видно.

---

## 3. Что это значит на практике

### 3.1. Уровни

Каждая станция — **отдельный `.tscn`**, который открывается и редактируется в редакторе.

```
scenes/stations/
├── station_base.tscn      # базовый шаблон: свет, туман, навигация, спавн-точка игрока
├── shelter.tscn           # убежище
├── station_akio.tscn      # станция
└── tunnel_akio.tscn       # тоннель
```

Геометрия — узлы прямо в сцене:

```
station_akio (Node3D)
├── Geometry (Node3D)
│   ├── Floor            MeshInstance3D
│   ├── Walls            MeshInstance3D + StaticBody3D
│   ├── Ceiling          MeshInstance3D
│   └── Platform         MeshInstance3D
├── Objects (Node3D)
│   ├── Door_Service     ← инстанс door.tscn
│   ├── Locker_A         ← инстанс locker.tscn
│   ├── Container_B      ← инстанс container.tscn
│   └── Terminal_01      ← инстанс terminal.tscn
├── Characters (Node3D)
│   └── Kitsu            ← инстанс kitsu.tscn
├── Lights (Node3D)
│   ├── EmergencyLight_01   OmniLight3D
│   └── Fluorescent_01      OmniLight3D
└── Markers (Node3D)
    ├── PlayerSpawn      Marker3D
    ├── Exit_ToShelter   Marker3D
    └── Zone_Platform    Area3D
```

**Всё это видно и двигается.** Никакой генерации из данных.

### 3.2. Объекты и персонажи

Переиспользуемые объекты — **отдельные сцены**, которые расставляются как инстансы.

```
scenes/objects/
├── door.tscn          # три состояния: заперта / открыта / выбита
├── container.tscn     # своя сетка предметов
├── locker.tscn
├── terminal.tscn
├── breaker.tscn       # рубильник
└── item_pickup.tscn

scenes/characters/
├── kitso.tscn
├── hayato.tscn
└── npc_base.tscn      # шаблон для остальных
```

Дверь на станции — это **инстанс `door.tscn`**, а не строчка в массиве. Можно выделить, подвинуть, повернуть, переопределить свойства в инспекторе.

### 3.3. Игрок и интерфейс

```
scenes/player/player.tscn      # CharacterBody3D + Camera3D + SpotLight3D (фонарик)
scenes/ui/hud.tscn             # CanvasLayer: HUD, инвентарь, диалог
scenes/systems/world_root.tscn # autoload: состояние мира, сохранение
```

### 3.4. Настройка через инспектор, а не через код

Всё, что может отличаться от объекта к объекту, — **`@export` переменные**, а не константы в скрипте:

```gdscript
@export var door_id: String = ""
@export var is_locked: bool = true
@export var needs_keycard: bool = false
@export var break_force: int = 3
@export var noise_radius: float = 4.0
@export var open_sound: AudioStream
```

Разработчик меняет поведение двери **в инспекторе**, не открывая скрипт. Один `door.tscn` — десять разных дверей на станции, каждая настроена по-своему.

## 4. Чего НЕ делать

| Нельзя | Почему |
|---|---|
| Строить уровень кодом в `_ready()` | В редакторе пусто. Нельзя подвинуть, не переписав код |
| Хранить объекты массивами словарей | Не узлы. Не видны, не выделяются, не настраиваются |
| Загружать геометрию из `.txt` / `.json` / `.tres` в рантайме | Та же ошибка, что в прототипе |
| Спавнить объекты из «таблицы спавнов» | Дверь должна лежать в сцене, а не создаваться из координат |
| Держать поведение в константах скрипта | Заменить на `@export`, чтобы правилось в инспекторе |
| Генерировать меши процедурно на старте | Уровень собирается руками, а не алгоритмом |

**Данные в `.tres` / `.json` допустимы** — для того, что не является частью уровня: диалоги, тексты предметов, описание предметов, конфиги. **Но не для геометрии и не для расстановки объектов.**

## 5. Приёмы, которые делают сцены удобными

### Наследование сцен

`station_base.tscn` задаёт общее (свет, туман, точки спавна), конкретные станции наследуются от него и переопределяют своё. Так каждая станция не пересобирается с нуля.

То же для персонажей: `npc_base.tscn` → `kitsu.tscn`, `hayato.tscn`.

### Группы вместо жёстких путей

```gdscript
get_tree().get_nodes_in_group("doors")
get_tree().get_nodes_in_group("light_sources")
```

Позволяет находить объекты без привязки к структуре дерева.

### `@tool` где нужно

Если объект должен выглядеть правильно **в редакторе** (например, спрайт разворачивается по нужному направлению, или рисуется зона шума), — пометить скрипт `@tool`.

### Сигналы вместо прямых вызовов

Дверь сообщает о вскрытии сигналом. Кто слушает — не её дело. Так объекты не связаны друг с другом жёстко.

### Именование

Узлы называть по смыслу: `Door_Service`, `Locker_A`, `EmergencyLight_01`. Не `Node3D`, не `Node3D2`, не `Sprite3D7`.

## 6. Проверка перед сдачей

Прежде чем сказать «готово», открой в редакторе и проверь:

- [ ] Станция открывается как `.tscn` и **видна целиком**
- [ ] Стены, пол, объекты, свет, NPC — **отдельные узлы**, их можно выделить
- [ ] Объекты **двигаются мышкой** и не ломаются
- [ ] Дверь можно **перетащить, повернуть, настроить в инспекторе**
- [ ] Свойства объектов меняются **без правки скрипта**
- [ ] Запуск из редактора даёт то, что видно в редакторе
- [ ] **Нет кода, который строит уровень в рантайме**

Если хотя бы один пункт не выполняется — переделай, прежде чем идти дальше.

---

## 7. Почему это важнее скорости первого дня

Соблазн — быстро накидать уровень кодом, «потом переделаем». Так уже было в прототипе: код строил мир, и через год стало невозможно развивать.

**Сцены — это инвестиция.** Первый день может пройти медленнее, зато каждый следующий уровень собирается за часы, а не за переписывание генератора.

Проект должен **развиваться годами**. Сцены — то, что это позволяет.
