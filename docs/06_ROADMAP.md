# 06 — ПЛАН РАБОТ

> Отвечает на вопрос «с чего начать и как не утонуть».
> Главное правило: **не начинать с миграции**. Начинать с вертикального среза.

---

## 1. Принцип

Переписать 11 400 строк «правильно» невозможно. Каждая попытка сделать это приведёт к новой недоигранной демке.

**Вместо этого:** маленький срез, доведённый до играбельности. Если получается — расширяем. Если нет — знаем об этом на третьей неделе, а не на третьем месяце.

---

## 2. Порядок этапов

### Этап 0. Решения и документы

**Статус:** частично сделано (этот пакет).

Что осталось решить до кода:

- [ ] Финальный арт-стиль: пиксель-арт или рисованная графика? (референсы `Fallen Aces` и `MOUSE` — это **рисованная** графика, а не пиксель; прототип — пиксель. Решить, куда идём.)
- [ ] Судьба d20-проверок: оставить, упростить или убрать?
- [ ] Минимальная разрядность спрайтов: 4 направления или 8?
- [ ] Формат уровней: встроенный редактор, CSG или брашевый редактор?
- [ ] Нужны ли 3D-модели вообще, или всё спрайты?

**Выход этапа:** решения зафиксированы в этом пакете.

---

### Этап 1. Вертикальный срез

**Цель:** доказать, что базовая формула работает в 3D с спрайтами.

**Не делать:** миграцию систем, перенос контента, генерацию уровней.

**Сделать одну маленькую станцию:**

```
Комната убежища
  → короткий тоннель
  → запертая дверь
  → боковая комната
  → один интерактивный объект
  → возвращение в убежище
```

**Что должно работать:**

- [ ] Движение от первого лица (`CharacterBody3D` + `Camera3D`), обычный mouse-look
- [ ] Три спрайтовых объекта: NPC, предмет, контейнер
- [ ] Одна дверь — открыть / заперта / взломать / выбить
- [ ] Фонарик с зарядом, двусторонний
- [ ] Шум: брошенный предмет создаёт событие, мир реагирует
- [ ] Один диалог с ветвлением
- [ ] Переход между двумя сценами
- [ ] Сохранение и загрузка состояния
- [ ] Визуальный стиль: фильтрация `Nearest`, CRT поверх

**Критерий готовности:** в это можно играть 5 минут и не хотеть закрыть. Если да — база верна.

**Оценка:** ~2–4 недели работы одного человека при готовых ассетах.

---

### Этап 2. Системы-фундамент

По одной, в порядке из `03_SYSTEMS.md` п.12:

- [ ] **Шум → реакция мира.** Полноценная система: источник → радиус → реакция
- [ ] **Свет → зрение.** Освещённость влияет на видимость
- [ ] **`use X on Y`.** Общая система, не список пар
- [ ] **Персистентность.** Состояния объектов между циклами
- [ ] **Электричество.** Рубильник → сеть → свет, двери, терминалы

**Критерий готовности:** заготовленную ситуацию можно пройти 3+ ортогональными способами, и игрок находит четвёртый.

---

### Этап 3. Контент

Только после того, как фундамент держит нагрузку.

- [ ] Порт интерфейса: HUD, инвентарь 6×5, диалоговое окно, контекст-меню
- [ ] Порт 8 предметов с флейвор-текстами
- [ ] Порт анимаций рук (7 наборов)
- [ ] Диалоги: Китсу, Хаято, странник
- [ ] Материалы из 16 МБ существующих текстур
- [ ] Убежище как полноценная локация
- [ ] Станция Акио как первая боевая станция (без угроз — только среда)

---

### Этап 4. Угрозы и столкновения

**Только здесь.** И только когда exploration loop доказан.

Проектировать заново, не переносить. Возможные направления:

- избегание (угроза, которую нельзя победить);
- отвлечение (шум, свет);
- социальные решения (договориться, обмануть);
- преследование (динамика, а не статика);
- временное обезвреживание;
- редкие столкновения с последствиями для Humanity.

**Не тащить** старую модель конечностей и боевой UI.

## 3. Что делать НЕ надо (список соблазнов)

| Соблазн | Почему плохо |
|---|---|
| Написать универсальную ECS | Иммерсив-сим провоцирует. Начинать с 10 объектов |
| Автоконверт ASCII-карт | Загонит в ту же клеточную парадигму |
| Перенести все 11 систем сразу | Раздувает срез, убивает сроки |
| Сделать «правильно» до игры | Нет играбельности — нечего исправлять |
| Написать свой рендер заново | Мы именно от этого уходим |
| Сразу 8 направлений спрайтов | 4 хватит для проверки. Художник нарисует больше потом |
| Сразу большая карта | 5 комнат показывают больше, чем 50 пустых |

## 4. Контрольные вопросы на каждом этапе

Задавать себе регулярно. Если ответ «нет» — что-то идёт не так.

1. **Играбельно ли это прямо сейчас?** Можно запустить и пройти?
2. **Есть ли 3+ способа пройти заготовленную ситуацию?**
3. **Мир помнит, что сделал игрок?**
4. **Работают ли системы вместе без специальных исключений?**
5. **Было ли за сессию «а так было можно?»**
6. **Читается ли картинка без CRT-шейдера?**

## 5. Технические заметки для того, кто начнёт

### Работа с прототипом

- Прототип — **архив**, не база. Не рефакторить его, не «дочищать». Он свою задачу выполнил.
- Готовые ассеты — в `assets_anchor/`.
- Ловушки при чтении старого кода — в `05_PROTOTYPE_AUDIT.md` п.5.

### Проверка в песочнице

Прототип запускается headless (`Godot 4.7.2` проверен):

```bash
godot --headless --import                      # импорт проекта
godot --headless --quit-after 300 res://scenes/...  # прогон сцены
```

Станция на текущем `master` грузится **без ошибок**. Боевая сцена — падает (баг с mp3, см. аудит).

Рендер кадра возможен через программный Vulkan (`lavapipe` + `Xvfb`), без видеокарты.

### Git

Прототип заморожен на `master`. Новая работа — в отдельной ветке (`next-3d`).

Коммиты в прототипе подписаны `Project Developer <dev@project-butterflies.local>` — не привязаны к аккаунту GitHub. Наследие, менять не обязательно.

## 6. Первый шаг

Если нужно начать **сегодня**:

1. Прочитать `01_VISION.md` — понять, что за игра.
2. Создать пустой Godot-проект, ветка `next-3d`.
3. Сделать один куб, одного спрайтового NPC, одну кнопку и одностороннюю дверь.
4. Запустить, пройти туда-обратно.

Всё. Остальное вырастет из этого куба. Не из архитектурного плана — из работающего движения.

> **Помни:** главный приоритет проекта — удивлять. Первый прототип, который удивит тебя самого через пять минут игры, лучше любого, который "правильно спроектирован".
