# 04 — ТЕХНИЧЕСКОЕ НАПРАВЛЕНИЕ

> Отвечает на вопрос «как это собирать».
> Ключевое решение: **3D-пространство + спрайтовые персонажи и объекты.**

---

## 1. Почему уходим из рейкастера

Текущий прототип — собственная реализация рейкастера (в духе Wolfenstein 3D) на GDScript. Он рабочий и атмосферный, но как фундамент для большой игры непригоден.

**Проблемы:**

| Проблема | Как проявляется |
|---|---|
| Собственный рендер | `dungeon_renderer.gd` — ~860 строк: стены, пол, спрайты, ZBuffer, туман, контур, полёт-дуга |
| Раздутый координатор | `dungeon_gameplay.gd` — 716 строк: собирает 12 систем |
| Всё завязано на сетку | `grid_x`, `grid_y` у каждой сущности; взаимодействие через клетку перед игроком |
| Нет вертикальности | Высота эмулируется, полноценные этажи и балконы невозможны |
| Каждая новая механика | Требует правки собственного рендера |
| Редактор редактирует не уровень | А набор данных для самописной проекции |
| Fog of war, свет, 7 тайлов | Всё вручную, всё в одном файле рендера |

**Диагноз:** это не «плохо написанный код». Это исчерпание подхода. Каждая новая фича стоит всё дороже, а возможности не растут.

**Решение:** переписать на штатных средствах Godot. Не потому что 3D «лучше», а потому что **движок уже умеет то, что мы пишем руками** — и пишет это лучше нас.

---

## 2. Визуальное направление: спрайты в 3D

Пространство — полноценное трёхмерное. Персонажи и часть объектов — плоские спрайты.

Это не компромисс, а **осознанный стиль**. Приём старый и проверенный: `Doom`, `Duke Nukem 3D`, `Blood` делали именно так. Современные продолжатели:

### Fallen Aces

Псевдо-3D (2.5D) в стиле комикса. Crime noir, кадры как из комиксов. Спрайтовые персонажи в трёхмерном пространстве — заметно, что плоские, и это работает как художественный приём.

### MOUSE: P.I. for Hire

Rubber hose анимация 1930-х, чёрно-белый нуар, вручную нарисованные кадры. Тоже полноценный FPS с плоскими рисованными объектами.

**Общее у обоих:** высокая детализация рисовки, узнаваемый стиль, спрайты выглядят намеренно плоскими, и игра от этого не страдает, а выигрывает.

**Что это значит для нас:** не нужно 3D-моделей персонажей. Не нужен 3D-аниматор. Нужен художник и система, которая правильно показывает спрайты в 3D.

> **Важно:** обе игры — стилистически цельные. У них 2D-анимация и 3D-мир сделаны в одном ключе. У Project Butterflies ключ свой: пиксель-арт + токийское метро + CRT. Стиль задаём мы, а не референсы.

## 3. Как реализуются спрайтовые персонажи в Godot

Четыре подхода. Рекомендую начать с первого, при необходимости комбинировать.

### 3.1. Billboard (рекомендуемый старт)

`Sprite3D` или `AnimatedSprite3D`, всегда повёрнутый к камере.

- **Плюсы:** быстро, дёшево, использует существующие PNG, 4–8 направлений легко.
- **Минусы:** вблизи заметно плоскость.
- **Для кого:** NPC, дальние силуэты, простые сущности.

В Godot есть `billboard_mode` у `Sprite3D` (`BILLBOARD_ENABLED`, `BILLBOARD_FIXED_Y`, `BILLBOARD_Y_BILLBOARD`). Для трупов и лежащих объектов нужен `FIXED_Y`, иначе они будут вставать на камеру.

### 3.2. Cross-plane / перекрещенные плоскости

Две-три пересекающиеся плоскости с одним спрайтом.

- **Плюсы:** читается при обходе, сохраняет объём.
- **Для кого:** крупные объекты, растительность, колонны.

### 3.3. Направленные спрайты

Набор кадров на 4–8 направлений, выбор по вектору `персонаж → камера`.

- **Плюсы:** контроль качества ракурса, знакомый подход из прототипа.
- **Для кого:** именные NPC, важные существа.
- **Требование:** художник должен нарисовать каждое направление.

### 3.4. Гибрид

Тело — спрайт, отдельные элементы — 3D или отдельные слои:

- оружие/руки — модели или слоистые спрайты;
- светящиеся элементы — `Sprite3D` с эмиссией;
- тень — blob shadow (простой диск);
- движение — шейдер или частицы.

## 4. Рендер и стиль

### Настройки, задающие пиксельный вид

| Настройка | Значение | Зачем |
|---|---|---|
| Filter | `Nearest` | Без размытия пикселей |
| Viewport resolution | Пониженный (напр. 320×240 → апскейл) | Единый пиксельный масштаб |
| Texture import | `Nearest`, без мипмапов | Чёткие текстуры |
| Палитра | Ограниченная | Цельность |

### Постобработка

- **CRT-шейдер** — есть готовый (`crtshader.gdshader`), переносить.
- **Fog** — есть `fog.gdshader`, `light_fog.gdshader`. В 3D делать через `WorldEnvironment` + volumetric или шейдер.
- **Outline** — есть `outline.gdshader`, использовался для наведения.
- **Dither и шум** — для атмосферы.

**Правило:** сначала сцена должна читаться **без** постобработки. CRT поверх кривой картинки маскирует проблемы с освещением и контрастом. Накладывать в последнюю очередь, не первой.

### Освещение

В 3D получаем бесплатно то, что в прототипе писали руками:

- реальные источники света (`OmniLight3D`, `SpotLight3D`);
- тени;
- запечённый свет (lightmap) для статики;
- туман как объёмная среда;
- приоритеты света и слои видимости.

Фонарик — `SpotLight3D` на камере. Заряд и батарейки — геймплейная логика поверх.

### Ключевое архитектурное отличие от прототипа

**Прототип:** сущности — словари в массиве. Взаимодействие — по координате клетки.

```gdscript
# Было
if ent.get("type") == "enemy": ...
var front_tile = map[grid_x][grid_y]
```

**Новая версия:** сущности — узлы. Взаимодействие — через интерфейс объекта.

```gdscript
# Стало
var target := interaction_ray.get_collider()
if target is Interactable:
    target.get_available_actions(context)  # объект сам знает, что можно
    target.interact(action_id, context)
```

Объект сам сообщает доступные действия, требуемые предметы, производимый шум и последствия. Никаких `if type ==` по всему коду.

## 6. Сохранение логики в 3D: зоны вместо сетки

Отказ от сетки — главный риск. Потерять дискретность легко, а с ней удобство авторинга.

**Решение: разделить визуальное и логическое пространство.**

```
Визуально:  полноценный 3D, свободное движение, физика
Логически:  станция → зоны → точки интереса
```

Игрок ходит свободно. Но станция по-прежнему структурирована:

```
station_akio
├── Zone_Platform          # зона: платформа
├── Zone_ServiceTunnel     # зона: служебный тоннель
├── Zone_LockedSector      # зона: закрытый сектор (открывается позже)
├── POI_TicketOffice       # точка интереса
├── POI_BrokenTerminal
└── Exit_ToShelter         # выход
```

События привязаны к зонам и точкам интереса, а не к клеткам. NPC-расписание работает по зонам. Сохранение — по именам объектов.

Это даёт свободу 3D и управляемость авторинга.

## 8. Что технически НЕ делать

**Не конвертировать ASCII-карты автоматически в финальные уровни.** Можно сделать временный генератор «ASCII → blockout-геометрия» для быстрых серых прототипов, но финальные уровни должны строиться как 3D-сцены. Автоконверт загонит в ту же клеточную парадигму, из которой мы уходим.

**Не создавать «абстракцию на будущее» там, где её требует воздух.** Иммерсив-сим соблазняет написать универсальную ECS для всего. Начинать надо с 10 интерактивных объектов, а не с фреймворка.

**Не тащить `StationData` как основной формат уровня.** Он был удобен для ASCII-карт. В 3D уровень — это сцена; метаданные станции (название, выходы, флаг безопасной зоны) остаются, но не как единственный источник геометрии.

**Не переносить собственный рендер ни в каком виде.** Ни ZBuffer, ни floor projection, ни ручную сортировку спрайтов. Всё это делает движок.

**Не смешивать прототип и новую версию в одной ветке.** Старый код — архив, новый — отдельная ветка.

## 9. Рекомендуемые ветки

```
master        — замороженный прототип (историческая ценность)
prototype-2d  — если master занят чем-то другим
next-3d       — новая реализация
design        — документы, референсы, концепт-арты
```

Прототип **не удалять**. Он — референс того, как игра ощущалась, и источник готового контента (ассеты, диалоги, тексты предметов).
